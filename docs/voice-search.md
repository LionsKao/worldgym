# 語音搜尋：完整設計紀錄

> 這份是從 CLAUDE.md 逐字搬過來的原文（2026-11-20 搬遷，內容沒有改動）。CLAUDE.md 只留語音搜尋的現行設計摘要與改動時的地雷；要改相關程式之前先讀這份。
> 內文提到「某段」若指的是 CLAUDE.md 的段落，請回 CLAUDE.md 找；提到的日期是當時使用者做決定、回報問題的日期。

**語音搜尋**（使用者 2026-11-09 決定；2026-11-10 用 iPhone 實測通過後正式開放給所有人，沒有開關、沒有偏好設定）。下面只寫**目前**的設計與原因，演進過程與被推翻的實驗不留（要查看 `git log`）。

- **入口**：篩選頁**完全沒勾選任何篩選**時（`hasAnyFilterSelected()`，跟 `#resetFiltersBtn` 的灰色條件同一個，故意比 `isSearchValid()` 更嚴格），查詢鈕的圖示從放大鏡換成麥克風（`.coral-btn`，紅色用 `--coral` 變數，不要寫死 hex）。有勾選任何篩選、瀏覽器不支援語音（`isVoiceSupported()` 為假，例如 Firefox）或麥克風權限被拒，一律維持放大鏡。**沒有確認畫面**：比對出分店／老師／課程／星期／時段／教室後直接勾選並送出查詢。聖誕樹、投票日印章兩個彩蛋優先（`xmasActive`／`voteActive` 為真時 `micEligible()` 回 false）。因為網站會還原上次勾選的條件，回訪的使用者多半有勾選、看到的是放大鏡，要按重置才看得到麥克風。
- **雙軌**：桌面／Android 用瀏覽器原生 `SpeechRecognition`；**iOS／iPadOS 完全不走 SpeechRecognition**，改成錄音上傳 Worker、用 Workers AI 轉文字。原因：iOS 第二次之後 `onstart`／`onaudiostart` 照樣觸發、底層音訊卻送不到辨識引擎，是 iOS `AVAudioSession` 狀態管理的平台問題（WebKit Bug #317741 已修但還沒進穩定版，相關的 #321436 未修），JS 層面繞不過。分流點是 `useRecorderVoice()`（`isIOS()` 且有 `MediaRecorder` 與 `getUserMedia`）；`isVoiceSupported()`＝兩條路徑擇一支援，`micEligible()` 與麥克風 Permissions API 查詢都看它。`isIOS()` 定義在語音區塊開頭（不要靠函式提升），含 `navigator.maxTouchPoints > 1` 辨識偽裝成 MacIntel 的 iPadOS，下載圖片的預覽視窗也用它。
- **狀態機**：`voiceRecognitionState` 單一四態字串：`"idle"`／`"starting"`（已按下、等權限視窗或 `onstart`）／`"listening"`／`"processing"`（收到結果、比對中；iOS 還包含上傳辨識）。`startVoiceSearch()` 一開始就設 `"starting"` 並鎖住（`setVoiceRecordingLock()`：`#resetFiltersBtn`／`#notifyBtn` 變淡並 disabled〔`.voice-dimmed`〕，**六組篩選 checkbox 也一起 disable**，不然聆聽或比對期間手動勾選會被語音結果的整組取代悄悄蓋掉）。`filterForm` 的 submit 監聽器：`"starting"`／`"processing"` 再點一律 return（所有平台，否則會落到 `performSearch("manual")` 跳出誤導的「請先選擇一些分店或老師」），`"listening"` 時是提前結束。
- **準備中／麥克風啟動中的提示**（使用者 2026-11-18 決定）：按下麥克風到真的開始收音之間（`"starting"`，兩條路徑都有）`#submitTooltip` 顯示單行「準備中」（`showVoicePreparingTooltip()`），進入 `"listening"` 時換成「聆聽中」，字一換就是「現在可以講了」的信號。原因：這段等待原本畫面完全沒回饋，使用者容易搶先開口、前幾個字沒收到。選「準備中」不選「啟動中」：跟「聆聽中」「辨識中」同樣三個字加「中」，意思是「先等一下」，「啟動中」聽起來偏技術。**兩段式**：等超過 `VOICE_STARTING_SLOW_MS`（750ms）還沒開始，才換成「麥克風啟動中」讓人知道為什麼比較久；熟了之後只會看到「準備中」一閃。**不預測冷暖，純看實際等了多久**：沒有 API 能事先知道系統暖了沒（Permissions API 的 `prompt`／`granted` 也不能用，Chrome iOS 暖的時候照樣回報 `prompt`），暖的狀態能撐多久也沒量過（只有連續按、間隔幾秒的資料）。失敗、逾時、取消都經過 `resetVoiceUI()` → `hideVoiceTooltip()`，不會留著；權限視窗還沒按時會一直顯示到逾時或按完。
  - **實機量到的數字**（2026-11-18，用臨時診斷畫面量，已刪除；iPhone）：按下到呼叫 `getUserMedia` 約 12～17ms、`getUserMedia` 回來到真的開始錄 8～19ms、`voice-search.js`／pinyin 在 60ms 內載完且不擋任何事——**我們的程式碼只佔不到 50ms，其餘全在 `getUserMedia` 內部（iOS 開麥克風），JS 動不了**。`getUserMedia` 本身：Safari 第一次 1215ms（權限已允許、沒跳視窗，是乾淨的冷啟動）；Chrome iOS 第一次 1687ms（**含權限視窗**，分不出冷啟動佔多少；Chrome 重新載入頁面後第一次按會再問一次，兩次實測都是）；之後每次（暖啟動）330～383ms。所以門檻 750ms 夾在暖（約 0.39 秒以內）與冷（約 1.2 秒以上）中間。
  - **沒做的做法與原因**：頁面載入時先偷開麥克風暖機、或用完不放開麥克風——都會在使用者沒操作時亮橘點，可能打斷正在播的音樂，Chrome 還會在載入時直接跳權限視窗。**沒試過的一個**：`getUserMedia` 的限制條件（例如只關掉 `echoCancellation`，我們不播放聲音）可能改變 iOS 初始化音訊的方式、也許更快，純推測、沒有數據；降噪與自動增益不要動，健身房很吵，可能影響辨識準確度。想再縮短冷啟動才值得試。
- **聆聽中的畫面**：查詢鈕維持紅色，外圍兩圈脈衝環＋鈕內等化器短條取代麥克風圖示（`.voice-listening`，只在 `prefers-reduced-motion:no-preference` 時換成等化器；減少動態效果的使用者保留靜態麥克風，不然圖示被藏起來又沒動畫會變成空的紅圓）。`#submitTooltip`：桌面是「聆聽中・請說話」加「再點一下或停頓即可結束」兩行；iOS 只有「聆聽中」三個字、提示框縮到剛好包住文字（使用者 2026-11-10 要求不顯示秒數、不讓使用者知道平台差異與實作，這個網站靠圖示就看得懂）。processing 時查詢鈕換成跟「查詢中」同一個轉圈圈（`computeSubmitIconClass()` 決定，`aria-label`「辨識中」），辨識完直接送出查詢時 `.busy` 的轉圈圈無縫接上。
- **共用比對流程 `runVoiceProcessing(getTranscript)`**：切 processing → 取得文字（桌面同步、iOS 是上傳轉錄）→ `loadVoiceSearch()` → `WGVoiceSearch.applyTranscript(transcript, isCurrent, onMatched)` 套用或送出 → `finally` 一定 `resetVoiceUI()`（任何一步丟例外都保證收尾，不會卡在 processing）。`voiceRunId`／`isCurrent`：取消會 `voiceRunId++`，這一輪若在載入比對引擎或 `await buildVocabulary()` 之後已過期，回 `"cancelled"`、什麼都不套用不送出。`cancelVoiceSearch()`（「清除篩選」會呼叫）也會 abort 進行中的上傳（`activeTranscribeController`，**要排在 `voiceRunId++` 之後**，上傳失敗時那一輪才看得出已過期、不跳錯誤）。失敗用 `VoiceFailure(reason, message)` 帶 GA reason 與使用者訊息。`applyTranscript` 回傳 `"no-match"`（完全沒聽懂任何類別，什麼都不碰，只顯示提示）、`"insufficient"`（聽懂一些但沒有分店或老師，跟 `isSearchValid()` 同一條規則，套用但不送出）、`"submitted"`（套用並送出）、`"cancelled"`。
- **SpeechRecognition 路徑（桌面／Android）**：
  - 每次 `startVoiceSearch()` 都 `new` 全新物件。停止聆聽三種方式：`continuous=false`（偵測停頓自動結束）、再點一次用 `recognition.stop()`（仍會觸發一次 `onresult`）、6 秒強制逾時（`VOICE_RECOGNITION_TIMEOUT_MS`）。**逾時計時從點下麥克風那一刻開始**，不是等 `onstart`：權限視窗沒回應時 SpeechRecognition 既不觸發 `onstart` 也不觸發 `onerror`，畫面會卡住。
  - **點擊到 `recognition.start()` 之間不能有任何 `await`／`.then()`**：`start()` 必須留在使用者點擊的同步呼叫鏈裡，否則 iOS Safari 可能整個收音悄悄失效且沒有任何錯誤訊息。所以用同步旗標 `recognitionReady` 擋重入：預設 true，建立新 session 設 false，該 session 的 `onend` 過 `RECOGNITION_COOLDOWN_MS`（400ms，`setTimeout` 放在 `onend` 這一側，不影響點擊當下的同步性）才設回 true，`start()` 丟例外則立即設回；太快再點會顯示「請稍候一下再試一次」並放棄這次點擊。
  - **已拿到結果的 session 不要手動 `abort()`／`stop()`**：`onresult` 只 `clearRecognitionSession()`（清計時器與提示），讓瀏覽器照 `continuous=false` 自己結束；手動中止會讓整個分頁的音訊狀態卡住、之後叫不動麥克風。逾時與取消（`handleVoiceTimeout()`／`cancelVoiceSearch()`）沒有結果可拿，仍用 `abortActiveRecognition()`。`document.visibilitychange` 切到背景且狀態是 `"starting"`／`"listening"` 時只呼叫 `resetVoiceUI()` 解鎖畫面、不碰底層物件（不含 `"processing"`，那時 recognition 已不歸我們管）。
  - 收尾一律先 `detachRecognitionHandlers()` 拔掉事件處理器再 abort／stop（`abort()` 之後瀏覽器仍會非同步觸發 `onerror("aborted")`／`onend`，不拔會重複處理、彈出矛盾的第二則「沒聽到聲音」並多送一次 `voice_search_failed`）。每個 session 的「使用者可見結果處理過了沒」是 `startVoiceSearch()` 閉包裡的 `settled`，物件上另掛 `recognition._markSettled` 給構不到閉包的收尾函式。
  - `onaudiostart` 偵測：`onstart` 不保證 `onaudiostart`（真的收到音訊，對應手機橘點）會來；`onstart` 後 `AUDIO_START_CHECK_MS`（2500ms，起始值）內沒收到、session 也還沒被處理，就顯示「麥克風目前無法使用，請重新整理頁面再試」（`reportVoiceFailure("mic-silent", …)`），刻意不說「再試一次」，因為這個情境已知再點沒用。
- **iOS 錄音路徑**：
  - 流程：點麥克風 → `"starting"` → `getUserMedia({audio:true})`（第一個 await，之前只有同步的狀態設定）→ `MediaRecorder`（`pickRecorderMimeType()` 優先 `audio/mp4`）→ `"listening"` → 再點一下或滿 `VOICE_RECORD_MAX_MS`（**7 秒**）→ `recorder.stop()` → `onstop` 放開麥克風（**每條 track 都要 `stop()`，狀態列橘點才會消失**）→ `"processing"` → `transcribeVoiceBlob()` 上傳 → 走 `runVoiceProcessing()`，**比對引擎跟桌面完全共用**。沒有靜音自動停止（要自己再點一下，不然等滿 7 秒）；要做的話用 `AudioContext` 分析音量，但 iOS 的 AudioContext 有自己的手勢限制。7 秒是 8 秒縮短來的（使用者 2026-11-12：後台平均音檔 148KB 已逼近 Worker 的 256KB 上限）；它同時是成本與上傳量天花板、也是沒再點時要等的時間，要放寬先看後台的 `too_large` 次數。若想進一步縮小上傳，可以替 `MediaRecorder` 設 `audioBitsPerSecond`（例如 32000），但會改變錄音品質，要用 iPhone 實機比對辨識準確度再決定（目前沒設，256KB 上限是照預設位元率估的）。
  - `cancelRecorderSession()`（停錄音、放麥克風、清 `activeRecorderSession`）**由 `resetVoiceUI()` 第一行呼叫**，取消、切到背景、失敗、逾時、兜底 `.catch` 每個出口都一併收乾淨，呼叫端不用各自記得（漏一處麥克風就一直開著、橘點一直亮）。「這個 session 已被取消／結束」就是 `activeRecorderSession !== session`，不另存旗標，`onstop`／`onerror`／`getUserMedia` 晚到的結果都靠它判斷（等權限期間被取消，晚到的 stream 會立刻放開）。錄音物件是我們自己持有的，這裡可以放心主動收。逾時：點下到拿到麥克風 `VOICE_RECORD_START_TIMEOUT_MS`（10 秒，共用 `handleVoiceTimeout()`）、上傳加轉錄 `VOICE_TRANSCRIBE_TIMEOUT_MS`（15 秒），都是起始值。錄音開始時順便預熱 `getQueryToken()`，讓換發跟錄音重疊。
- **Worker 端點 `POST /transcribeVoice`**（`worker/src/index.js` 的 `handleTranscribeVoice`，`limit: 10` 每 IP 每分鐘）：要帶 `/issueToken` 的 `X-Query-Token`（`queryToken: true`，沒帶對 401）；`Content-Type` 必須是 `audio/*` 或 `video/*`（iOS 的 mp4 有時被標成 video/mp4）；大小在 200 byte～`VOICE_MAX_BYTES`（**256KB**）：有 `Content-Length` 且過大直接 413，沒有（chunked）由 `readBodyCapped()` 邊讀邊算、超過就中止回 413，不會把整個 body 讀進記憶體；成本是照「音訊秒數」算而 Worker 只量得到位元組，上限不要放寬回 1MB（低位元率的 1MB 能塞十幾分鐘）。格式與大小都通過後才扣**全站每日額度** `VOICE_DAILY_LIMIT`（2000 次，KV `voice-daily:<台灣日期>`，`takeKvQuota()` 非原子只求大致準確，超過回 429、前端顯示「操作太頻繁」，使用者仍可手動查詢；格式不對或太小的請求不耗額度）。用 `env.AI.run("@cf/openai/whisper-large-v3-turbo", { audio: base64, language: "zh", vad_filter: true, initial_prompt })`（直接用 Workers AI binding，`wrangler.toml` 的 `[ai] binding = "AI"`；音檔讀取與 base64 用 `Buffer`，`nodejs_compat` 已開）。**音檔只存在這次請求的記憶體，不寫 D1／KV、不進 log。** 海外爬蟲不放行（不在 `crawlers.js` 的唯讀白名單）。`wrangler dev` 本來就是 `--remote`，本機測試會消耗極少量正式帳號的 Workers AI 額度。
  - `initial_prompt` 用繁體寫（Whisper 預設中文常輸出簡體，比對引擎詞彙全是繁體），**但刻意不放任何具體的分店／星期／課程**（`VOICE_PROMPT_PHRASE`：「以下是繁體中文的語音搜尋，內容是健身房的課程、老師和分店」）：Whisper 遇到太短、太吵的音訊常把提示語原句吐回來，而語音比對到完整條件會不經確認直接送出，提示語若是個有效查詢（例如台北大安分店加星期三晚上），被複誦就會讓使用者莫名其妙看到一組沒講過的結果。再保險一層：`stripPromptEcho()` 把回傳文字裡的整句提示語拿掉（純複誦變空字串，前端顯示「沒聽清楚」）；`vad_filter` 讓純靜音回空字串。**調整提示語要用真人在 iPhone 上錄的音檔驗證**（本機用 Windows 的 zh-TW 語音合成測過，合成語音偶爾有同音錯字，拼音容錯能接住）。
  - **成本**：whisper-large-v3-turbo 約 46.63 Neurons／音訊分鐘，免費額度每天 10,000 Neurons ≈ 214 分鐘；每次最多 7 秒（約 0.12 分鐘、約 5.4 Neurons），就算 7 天活躍 449 人、人均 6.3 次查詢全部改語音也遠低於免費額度。惡意上傳的最壞情況靠三道一起擋（token＋每 IP 每分鐘 10 次、256KB 大小上限、全站每日 2000 次）：每次最多 256KB 的極低位元率音訊（約 5～6 分鐘、約 270 Neurons），一天 2000 次也只是數十萬 Neurons，是有上限的數字。帳號是 Workers Paid，超過免費額度依用量計費、不會停掉，可在 Dashboard 設用量通知。每日額度是全站共用，被耗光時所有 iPhone 使用者的語音都會被擋到隔天（沒有通知，只有後台看得到）。
- **隱私**：`index.html` 的 `#privacyTooltip` 寫了「iPhone／iPad 的語音搜尋會把語音傳到 Cloudflare AI 轉成文字，不儲存錄音；其他裝置使用瀏覽器內建的語音辨識，語音會傳給瀏覽器廠商（如 Google）處理。」這句是「語音會離開使用者裝置」的揭露，不是操作說明，不要為了精簡整句刪掉；**以後若改變音檔處理方式（例如開始留存），要同步改這句。**
- **後台「語音」面板**（`admin.html`、`admin.js` 的 `loadVoiceStats()`／`renderVoiceStats()`）讀 `GET /voiceStats`（`admin: true`，回近 30 天 `voice_daily` 的原始列，加總、補 0 的日期、成功率、平均值都在前端算）。顯示今日／近 7 天請求數、近 7 天成功率、平均音檔大小與耗時（近 30 天，只算真的送進 Workers AI 的 `ok`／`empty`／`ai_error`）、今日額度（這三種就是計入額度的）、近 30 天每日折線圖、依結果分類的表格；「語音」標籤本身是連到 Cloudflare Workers AI 用量頁的連結（`#voiceUsageLink`，實際花費以那一頁為準，Worker 量不到秒數）。面板底部刻意沒有說明文字。`recordVoiceOutcome()` 在 `handleTranscribeVoice` 各出口寫一筆：`ok`／`empty`／`ai_error`／`too_large`（有與沒有 `Content-Length` 兩種都記，後者位元組記 0）／`too_small`／`daily_limit`；token 錯誤（401）、格式不對（415）、每 IP 限流在進 handler 前就被擋，不計入（想看每 IP 的呼叫可在 `ROUTES` 加 `logAccess: true`，使用者還沒決定要不要開）。寫入放 `ctx.waitUntil` 且整段 try/catch，**D1 寫入失敗只記 log、絕不影響轉錄結果**。`voice_daily` 由 `migrations/022_voice_daily.sql` 建立（已套用到正式庫）。`common.js` 的 `monthTickLabel` 也認 `"YYYY-MM-DD"`（只顯示「月/日」）給每日折線圖用。**只涵蓋 iOS／iPadOS**；桌面與 Android 的原生辨識不經過 Worker，沒有任何成功率或使用量數據，只能看 GA（`start_voice_search` 在錄音路徑帶 `engine:"recorder"`、`voice_search_failed` 的 reason 見 `GA_EVENTS.md`）。

  - **同音字容錯（拼音）**：精確比對之後再把整句與詞彙轉拼音（`vendor/pinyin-pro.min.js`，`traditional:true`，準確優先、約 145KB gzip，由 `voice-search.js` 另外非同步載入；還沒載入完就跳過、退回純精確比對，不報錯）比一次，兩次結果取聯集。拼音詞彙至少 `MIN_PINYIN_TERM_LEN`（4 個字母）才收，太短的拼音太容易誤判；**純英文／數字的詞（老師 Bang、課程 BODYPUMP、別名 pump…）完全不參加拼音比對**（它們的「拼音」就是自己，只會跟句子裡的中文音節撞到巧合，例如「請**幫**我找…」的 bang 曾經誤中老師 Bang；真的講英文名字時精確比對本來就比得到），夾有中文的名字（小Ben、翔翔H）仍照轉，所以「小本」→ 小Ben 照常運作。**只有一個字的中文名字也不參加拼音比對**（`MIN_PINYIN_SYLLABLES`，純中文的詞至少 2 個字）：4 個字母的門檻擋不住單音節的長拼音，老師「炫」「軒」(xuan) 曾被任何念 xuan 的常用字誤中（「我想**選**課」→ 查老師炫，結果頁還把「選」標紅）；真的講「炫」，精確比對照樣比得到。**純中文的詞還要核對自己的音節切法**（`scanTerms` 的 `inner`）：句子裡的拼音切點必須跟詞完全一致，不然兩個音節接起來剛好等於另一個字的單一音節時會撞到——分店「吉安」(ji|an) 的拼音 jian 曾被任何念 jian 的字（「我想**健**身」「什麼時**間**有課」「再**見**」）誤中；「雞安」(ji|an) 這種切法一致的同音字仍然有效。夾英文的詞不核對切點（英文字母在逐字拼音裡每個字母各算一個元素，跟中文音節對不上）。**拼音比對必須對齊字的邊界**（`scanTerms` 的 `boundaries`）：只能從一個字的開頭比到一個字的結尾，否則「板橋」banqiao 會從 ban|qiao 中間切進去誤中老師「安起」anqi。範圍用 pinyin-pro 的逐字陣列換回字的位置，所以同音錯字（「戰前」→站前、「雄大」→熊大）也標得出來。不同的字剛好同音時（好豪／浩浩／皓皓／豪豪）：同音的拼音詞只有排最前面的那一個佔得到那段字，所以講其中一位，會是「講的那位＋清單裡排最前面的另一位」，不是全部同音者一起選到。
